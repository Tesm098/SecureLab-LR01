## 2. Власна реалізація і межі

### 2.1. CP-01: DTO boundary та безпечна реєстрація

Файл `src/SecureLab.Api/Scaffolding/Lab03Identity.cs` — `POST /api/auth/register`.

Контракт вхідного DTO `RegistrationInput`: `userName`, `email`, `displayName`, `password`. Перевірено обов'язковість усіх полів; `userName` — від 3 до 256 символів із дозволених `A–Z`, `a–z`, `0–9`, `.`, `_`, `@`, `+`, `-`; `email` — формат поштової адреси та не більше 256 символів; `displayName` — 1–120 символів. Тільки профільні поля `userName`, `email`, `displayName` нормалізуються через `Trim()`. Значення password не нормалізується й не записується до журналу.

Об'єкт `ApplicationUser` створюється на сервері з новим `Guid`, без ручного заповнення `PasswordHash`. Перевірку політики пароля, його хешування та збереження виконує стандартний `UserManager.CreateAsync(user, password)`; після створення сервер призначає роль `Reporter`, не приймаючи роль із JSON. За успіху endpoint повертає `201 Created` та окремий `RegistrationResponse(Id, UserName, DisplayName)`, за некоректного або повторного запиту — обережну однакову відповідь `400` з `{"message":"Registration failed"}`. У дозволеному DTO відповіді немає password, hash, stamp, cookie чи token.

**Фактичний CP-01:** ручна навчальна сторінка `register-check.html` продемонструвала T-01 (`201`, `application/json; charset=utf-8`, три дозволені поля) і T-02 (`400`, повторна реєстрація, `Registration failed`). Навчальна сторінка після перевірки видалена з `Client/` і не входить до Git. T-03 підтверджено описом **схеми** таблиці `identity_users` без читання рядків: є стовпець `PasswordHash` типу `text`, окремого стовпця відкритого пароля немає. Фактичних hash-значень не переглядали й не публікували.

### 2.2. CP-02: login, cookie і verified principal у `/api/me`

Наданий `POST /api/auth/login` використовує `SignInManager.PasswordSignInAsync`, тобто перевірка пароля відбувається в Identity. Для невідомого користувача та неправильного пароля залишена однакова зовнішня відмова `401 Unauthorized` — причина не розкривається. Успішний вхід Alice через `auth-lab.html` дав `Login: 204`.

**Початковий дефект:** попередній `GET /api/me` довіряв клієнтському заголовку `X-Demo-UserId`. Після усунення перешкоди із frontend fallback окремим запитом без cookie із заявленим Bob Id `10000000-0000-0000-0000-000000000002` фактично отримано `200 OK`, `application/json` і профіль `bob`. Це доводило порушення довірчої межі.

**Виправлення:** endpoint отримує поточного користувача виключно через `UserManager.GetUserAsync(httpContext.User)` і позначений `.RequireAuthorization()`. Клієнтський `X-Demo-UserId` більше не використовується. Повторення **того самого** запиту з Bob Id, але без cookie, повернуло `401 Unauthorized`, `application/problem+json`. Після входу Alice `/api/me` повернув `200 OK` і тільки `id`, `userName=alice`, `displayName=Аліса Коваль`.

**Cookie-профіль:** використовується надана конфігурація ASP.NET Core Identity; за фактичним оглядом DevTools на локальному `http://localhost:5080` cookie мала `HttpOnly`, `SameSite=Lax`, `Expires=Session`; `Secure` не встановлений у локальному HTTP-середовищі. Цей локальний огляд **не доводить production HTTPS/TLS**. `HttpOnly` обмежує читання cookie через JavaScript, `Secure` — передавання лише HTTPS, `SameSite=Lax` зменшує певні міжсайтові надсилання. Жоден із цих атрибутів не робить клієнтський заголовок UserId надійним джерелом особи.

### 2.3. CP-03: захищене створення інциденту

Файл `src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs` — `POST /api/incidents`. Повністю збережено серверну валідацію з ЛР02: обов'язкові `title`, `description`, `severity`, `occurredAtUtc`, довжини 160/4000, допустимі значення severity, перевірка часу, нормалізація UTC та безпечний response DTO.

До маршруту додано `.RequireAuthorization()`. Параметр `HttpContext` дає змогу взяти `ClaimTypes.NameIdentifier` із перевіреного principal та перетворити на `Guid`. Фіксоване `OwnerUserId = DbSeeder.AliceId` замінено на `OwnerUserId = verifiedUserId`. У `CreateIncidentRequest` **немає** `ownerUserId`, `id`, `role` або `status`: сервер сам встановлює власника, ідентифікатор і статус.

Тест A-01 довів анонімну відмову `401` без redirect і Bearer challenge. Тест A-05 увійшов як Bob, додав до JSON чуже `ownerUserId` Alice, отримав `201 Created`, знайшов **новий** запис за поверненим Id у тестовій БД та порівняв фактичний `OwnerUserId` із `DbSeeder.BobId`. Перевірка пройшла: підміна не вплинула на власника. Приховане поле форми, ID у заголовку й інші дані клієнта не є механізмом контролю доступу.

### 2.4. Маршрут довіри та залишкові обмеження

Маршрут: JSON із credentials → `SignInManager` і стандартний Identity password verifier → Identity cookie → браузер автоматично додає cookie до запиту того самого origin → authentication middleware перевіряє cookie → claims формують `HttpContext.User` → захищений endpoint отримує verified user → для нового `Incident` сервер визначає `OwnerUserId`.

**Залишковий ризик:** cookie-based state-changing `POST` у цій лабораторній ще не має повної окремої CSRF-моделі; `SameSite=Lax` та HttpOnly самі по собі не усувають усі CSRF-варіанти. За методичкою це навчальний борг до ЛР06. Можливими точками account enumeration залишаються `POST /api/auth/register` (повторна реєстрація може різнитися за часом обробки) та `POST /api/auth/login` (ризик статистичного перебору спроб). На достатньому рівні збережено однакову зовнішню login-відмову `401` і загальне `400` для помилок реєстрації, але **rate limiting, аудит подій і logout не реалізовувалися**: вони належать рівню «Добре». Ресурсні правила доступу до чужих наявних інцидентів є предметом ЛР04, а не доказом A-05.
