## 2. Гіпотеза й REG-XSS-01

### 2.1. Гіпотеза

Значення `Incident.Description`, яке контролюється користувачем під час створення інциденту, зберігається в PostgreSQL, повертається сервером у JSON-полі `description` відповіді `GET /api/incidents/{id}` та передається клієнтським JavaScript до DOM.

У початковому коді значення потрапляло в `innerHTML`, тобто передавалося до контексту HTML-парсера.

Тому браузер міг інтерпретувати збережений користувацький текст як HTML і виконати JavaScript-обробник події.

### 2.2. Карта проходження даних

Повна карта міститься у файлі:

`docs/source-to-sink.md`

Основний потік:

| Крок | Джерело або компонент | Значення |
|---|---|---|
| Source | Форма `browser-lab.html` | Користувацький опис інциденту |
| Request | `browser-lab.js`, POST | JSON-поле `description` |
| Validation | Обробник створення інциденту | Перевірка серверного контракту |
| Storage | PostgreSQL, `incidents.description` | Збережений текст |
| Response | `GET /api/incidents/{id}` | JSON-поле `description` |
| Transformation | `response.json()` | `current.description` |
| Vulnerable sink | `browser-lab.js` | `innerHTML` |
| Fixed sink | `browser-lab.js` | `textContent` |

Значення залишається недовіреним незалежно від проходження серверної валідації та збереження в базі даних.

## 3. Стан до виправлення XSS

Після входу як Alice на сторінці `browser-lab.html` створено інцидент із канонічним маркером у полі Description.

Форма виконала створення через `POST /api/incidents`, після чого отримала створений запис за його GUID.

Фактичний результат повторного читання:

`GET: 200`

У DevTools було підтверджено, що JSON-відповідь містить збережене значення опису.

Водночас браузер відображав замість буквального тексту маркера значок зламаного зображення.

У вкладці Elements всередині `#description` створювався дочірній HTML-елемент `<img>`.

Після відображення опису контрольна команда повертала:

`'executed'`

Це підтвердило виконання навчального обробника події через небезпечний HTML sink.

### 3.1. Перевірка Morgan

В окремому приватному сеансі виконано вхід під користувачем Morgan із роллю Analyst.

Morgan відкрив інцидент Alice за GUID:

`23447c78-05ac-4218-b8af-f3840221e6cd`

Результат:

- HTTP: `GET: 200`.
- До читання маркер мав значення `null`.
- Після читання маркер повертав `'executed'`.
- У браузері з'являвся результат HTML-інтерпретації опису.

Таким чином, підтверджено **Stored XSS**: текст, збережений Alice, виконувався під час подальшого перегляду іншим авторизованим користувачем.

### 3.2. Негативний контроль Bob

В окремому сеансі Bob спробував переглянути той самий інцидент.

Фактичний результат:

- HTTP: `404 Not Found`.
- У браузері: `GET: 404`.
- Контрольний маркер: `null`.

Серверна авторизація ЛР №4 не дозволила Bob отримати чужий інцидент.

Однак для користувача Morgan, який мав законне право читання, XSS залишався можливим до виправлення DOM sink.

## 4. Першопричина та виправлення

### 4.1. Першопричина

У початковій версії `browser-lab.js` містилися дві небезпечні операції:

`document.querySelector("#description").innerHTML = current.description;`

`paragraph.innerHTML = comment.text;`

Обидві операції передавали недовірені рядки до HTML-парсера браузера.

Основне дослідження проведено для `Incident.Description`.

Поле `IncidentComment.Text` також виправлено, оскільки кінцевий стан ЛР №5 не повинен містити жодного з цих двох небезпечних sink.

### 4.2. Виправлення

У файлі:

`src/SecureLab.Api/Client/browser-lab.js`

виконано заміни.

**Опис інциденту:**

Було:

`document.querySelector("#description").innerHTML = current.description;`

Стало:

`document.querySelector("#description").textContent = current.description;`

**Текст коментаря:**

Було:

`paragraph.innerHTML = comment.text;`

Стало:

`paragraph.textContent = comment.text;`

Для звичайного тексту застосовано безпечний DOM API `textContent`.

Виправлення не змінює вміст бази даних і не видаляє спеціальні символи з опису.

Причина XSS усунена в місці відображення.

### 4.3. Повторна перевірка

Після виправлення повторно відкрито той самий інцидент із канонічним маркером.

Фактичні результати:

- `GET: 200`.
- Повний текст маркера відображається буквально.
- Значок зламаного зображення відсутній.
- У `#description` немає дочірнього елемента `<img>`.
- Контрольний маркер повертає `null`.

Аналогічну перевірку виконано в сеансі Morgan.

Результат під Morgan:

- `GET: 200`.
- Маркер відображається як текст.
- Контрольна команда повертає `null`.

Отже, XSS більше не виконується ані під Alice, ані під Morgan.

Використано текст:

`O'Brien написав "Київ — Ω"; 5 < 7 і 9 > 3; <b>жирний</b> текст.`

До виправлення браузер створював елемент `<b>`.

`document.querySelector("#description").textContent.length`

Це підтвердило, що виправлення не призвело до втрати довгого тексту.

**Передумови:** локальний API, PostgreSQL, тестові користувачі Alice та Morgan, гілка `lab/5-browser-xss`, канонічний маркер із `resources/lab05-marker.txt`.

**Негативний контроль (vulnerable state):**

3. Увійти як Alice.
4. Створити інцидент із канонічним маркером в Description.

6. Переконатися, що контрольна команда повертає `'executed'`.
7. У новому сеансі Morgan відкрити той самий GUID і повторити перевірку.

**Перевірка fixed state:**

1. Використати виправлений код, зберігши створений тестовий інцидент у локальній БД.
2. Оновити `browser-lab.html` із вимкненим кешем.
3. Перевірити, що контрольний атрибут до читання має значення `null`.
4. Відкрити той самий GUID.
5. Порівняти `description` у Network → Response із текстом у DOM.
6. Переконатися, що `#description` не містить дочірнього `<img>`.

## 6. Основний finding

**Назва:** Stored XSS через небезпечне відображення `Incident.Description`.

**Актив:** браузерний сеанс користувача та дані інциденту.

**Передумови:** користувач має можливість створити інцидент із власним описом; інший користувач має законне право його прочитати.

**Першопричина:** недовірене поле `description` передавалося до `innerHTML` без контекстно безпечного відображення.

**Вплив у локальному стенді:** спрацьовував канонічний нешкідливий маркер, який змінював атрибут одного контрольного DOM-елемента.

**Виправлення:** використання `textContent` для опису інциденту та текстів коментарів.

**Повторна перевірка:** маркер відображається буквально; контрольна команда повертає `null`; DOM не містить елемента `<img>`, створеного з опису.

**Залишковий ризик:** інші неохоплені DOM sinks, URL- та атрибутні контексти й сторонні скрипти потребують окремого аналізу. CSP не реалізовувалася в межах обраного достатнього рівня. Для cookie-based змінювальних операцій окремим завданням залишається CSRF-захист у наступній лабораторній роботі.

## 7. CORS і REG-CORS-01

### 7.1. Навчальна топологія

Для досліду використано три origins.

| Призначення | Origin |
|---|---|
| SecureLab API і штатний браузерний клієнт | `http://localhost:5080` |
| Дозволений навчальний probe | `http://localhost:4173` |
| Недозволений навчальний probe | `http://localhost:4174` |

Origin визначається схемою, хостом і портом.

Порти `4173` та `4174` створюють різні origins навіть на одному комп'ютері.

CORS визначає, чи дозволить браузер JavaScript зі сторінки одного origin прочитати відповідь іншого origin.

CORS не є заміною автентифікації, авторизації або CSRF-захисту.

### 7.2. Прогноз перед налаштуванням CORS

| Сценарій | Чи доходить запит до API? | Чи може JavaScript прочитати відповідь? | Причина |
|---|---|---|---|
| Same-origin `5080 → 5080` | Так | Так, якщо API дозволяє сам запит | CORS не потрібний |
| Simple GET `4173 → 5080` | Так | Ні без CORS-дозволу | Same-origin policy |
| Simple GET `4174 → 5080` | Так | Ні без CORS-дозволу | Same-origin policy |
| Direct HTTP через curl | Так | Не застосовується | curl не застосовує браузерну SOP |
| Preflighted request | Залежить від відповіді на OPTIONS | Залежить від CORS-дозволу | Теоретичний сценарій, практично не перевірявся на обраному рівні |

### 7.3. Команди запуску

API:

`dotnet run --project src/SecureLab.Api`

Дозволений probe:

`py -3 -m http.server 4173 --bind localhost --directory demonstrations/cors-probe`

Недозволений probe:

`py -3 -m http.server 4174 --bind localhost --directory demonstrations/cors-probe`

Команди запускалися в окремих терміналах із кореня `starter-project`.

Обидві навчальні сторінки успішно відкривалися в браузері.

### 7.4. Початкові результати до CORS-політики

До зміни `Program.cs` виконано однаковий запит:

`GET http://localhost:5080/health`

Спочатку зі сторінки `http://localhost:4173/`, потім зі сторінки `http://localhost:4174/`.

**Origin 4173:**

- API повертав `200 OK`.
- У відповіді не було `Access-Control-Allow-Origin`.
- Console показувала повідомлення `blocked by CORS policy`.
- JavaScript отримував `TypeError: Failed to fetch`.

**Origin 4174:**

- API повертав `200 OK`.
- `Access-Control-Allow-Origin` був відсутній.
- Console показувала помилку CORS.
- JavaScript не міг прочитати відповідь.

Отже, до налаштування політики прості GET-запити доходили до API, але браузер не відкривав їхні відповіді викликаючому JavaScript.

## 8. Реалізація CORS-політики

У `src/SecureLab.Api/Program.cs` зареєстровано політику:

`Lab05BrowserProbe`

Її основні налаштування:

- `WithOrigins("http://localhost:4173")`
- `WithMethods("GET")`
- `WithHeaders("X-Lab-Cors-Probe")`

Політика реєструється лише за умови:

`builder.Environment.IsDevelopment()`

У pipeline використовується порядок:

`UseRouting()` → `UseCors("Lab05BrowserProbe")` → `UseAuthentication()` → `UseAuthorization()`.

Таким чином, CORS middleware обробляє cross-origin запити до виконання перевірок автентифікації та авторизації.

Для рівня «Задовільно» дослід із credentialed requests не проводився, тому `AllowCredentials()` не додавався.

`AllowAnyOrigin()` та `AllowAnyHeader()` не використовувалися.

У Production навчальна CORS-політика не реєструється і не застосовується.

`200 OK`

### 9.2. Недозволений origin 4174

Той самий запит виконано зі сторінки:

`http://localhost:4174/`

У Network підтверджено:

`Origin: http://localhost:4174`

HTTP-відповідь API:

`200 OK`

Заголовок `Access-Control-Allow-Origin` був відсутній.

Console показала:

`TypeError: Failed to fetch`

У Network запит був позначений як `CORS error`.

Отже, політика не дозволила JavaScript із `4174` прочитати відповідь API.

### 9.3. Перевірка CORS та авторизації

З дозволеного origin `4173` виконано запит без cross-origin cookie:

`GET /api/incidents/20000000-0000-0000-0000-000000000001`

Фактичний результат:

`401 Unauthorized`

Console повернула число:

`401`

Це підтвердило, що CORS дозволив прочитати HTTP-відмову, але не надав анонімному користувачеві доступу до захищеного інциденту.

Серверна авторизація продовжує працювати незалежно від CORS.

## 10. Порівняння browser і direct HTTP

Для незалежної перевірки використано `curl.exe`.

Команда:

`curl.exe -i http://localhost:5080/health`

Фактичний результат:

- `HTTP/1.1 200 OK`
- `Content-Type: application/json; charset=utf-8`
- `{"status":"ready"}`

Далі виконано:

`curl.exe -i -H "Origin: http://localhost:4174" http://localhost:5080/health`

Фактичний результат:

- `HTTP/1.1 200 OK`
- `{"status":"ready"}`
- Заголовок `Access-Control-Allow-Origin` відсутній.

Це означає, що прямий HTTP-клієнт може прочитати відповідь API незалежно від дозволів CORS.

Водночас автентифікація, авторизація та серверна валідація продовжують застосовуватися до запитів.

| Клієнт | Фактичний результат | Чи доступна відповідь клієнту? | Контроль |
|---|---|---|---|
| Same-origin browser `5080` | `GET: 200` для дозволеного читання | Так | API authorization |
| Browser `4173` | `/health`: `200 OK` | Так | Exact CORS allowlist |
| Browser `4174` | API: `200 OK`, браузер: CORS error | Ні для JavaScript сторінки | Browser SOP/CORS |
| Direct HTTP `curl.exe` | `200 OK`, JSON response | Так | Серверні правила API, не browser SOP |

## 11. Регресія REG-CORS-01

### 11.1. Передумови

API працює в Development на:

`http://localhost:5080`

Два локальні сервери працюють на:

`http://localhost:4173`

`http://localhost:4174`

У `Program.cs` активна політика `Lab05BrowserProbe` з одним дозволеним origin.

### 11.2. Browser evidence

**Allowed origin:**

Зі сторінки `4173` виконати `fetch("http://localhost:5080/health")`.

Очікується:

- `200 OK`.
- JavaScript читає JSON.
- Response header `Access-Control-Allow-Origin` дорівнює `http://localhost:4173`.

**Disallowed origin:**

Зі сторінки `4174` виконати той самий запит.

Очікується:

- Простий GET доходить до API.
- У відповіді немає `Access-Control-Allow-Origin`.
- JavaScript отримує CORS error.
- У Network видно абсолютну адресу `http://localhost:5080/health` і Origin `4174`.

Усі зазначені результати фактично підтверджено в DevTools.

### 11.3. HTTP evidence

Для дозволеного origin виконано:

`curl.exe -i -H "Origin: http://localhost:4173" http://localhost:5080/health`

Фактично отримано:

- `HTTP/1.1 200 OK`
- `Access-Control-Allow-Origin: http://localhost:4173`
- `{"status":"ready"}`

Для недозволеного origin виконано:

`curl.exe -i -H "Origin: http://localhost:4174" http://localhost:5080/health`

Фактично отримано:

- `HTTP/1.1 200 OK`
- `Access-Control-Allow-Origin` відсутній
- `{"status":"ready"}`

Обидві відповіді також містили:

- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: no-referrer`

Це підтверджує правильний кінцевий стан CORS-політики.

### 11.4. Підсумкова таблиця CORS

| Сценарій | До policy | Після policy | Результат |
|---|---|---|---|
| Same-origin `5080` | Працював | Працює | CORS не потрібний |
| Simple GET із `4173` | CORS error | `200`, JSON доступний | Успішно |
| Simple GET із `4174` | CORS error | CORS error | Успішно |
| Direct HTTP | `200 OK` | `200 OK` | Успішно |
| Захищений GET без cookie з `4173` | Не перевірявся окремо | `401 Unauthorized`, статус доступний JavaScript | Успішно |

## 15. Висновки

У лабораторній роботі №5 досліджено повний шлях проходження поля `Incident.Description` від форми введення до браузерного DOM.

Виявлено небезпечне відображення через `innerHTML`, яке призводило до виконання нешкідливого навчального XSS-маркера.

На локальному стенді підтверджено Stored XSS під час перегляду інциденту користувачем Morgan після створення запису Alice.

Вразливість усунуто шляхом заміни `innerHTML` на `textContent`. Повторні перевірки довели, що збережений текст більше не інтерпретується як HTML.

Також налаштовано CORS-політику з точним allowlist: дозволено лише `http://localhost:4173`, тоді як `http://localhost:4174` залишається заблокованим для браузерного JavaScript.

Порівняння браузерних запитів і `curl.exe` підтвердило, що CORS контролює читання cross-origin відповідей у браузері, але не замінює серверну автентифікацію й авторизацію.
