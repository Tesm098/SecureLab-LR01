## 1. Мета роботи

Метою лабораторної роботи є дослідження браузерних механізмів безпеки, виявлення та усунення XSS-вразливості у вебклієнті SecureLab, а також дослідження політики Cross-Origin Resource Sharing (CORS).

Під час виконання роботи необхідно:

1. Визначити повний шлях проходження недовірених даних від користувацького введення до DOM.
2. Відтворити XSS за допомогою нешкідливого навчального маркера.
3. Усунути небезпечне відображення даних через `innerHTML`.
4. Підтвердити ефективність виправлення повторними перевірками.
5. Налаштувати CORS із точним списком дозволених origins.
6. Порівняти браузерні запити з прямими HTTP-запитами.
7. Виконати регресійне тестування та підготувати Git-артефакти.

### 3.5. Усунення XSS-вразливості

У файлі `browser-lab.js` замінено дві небезпечні операції.

**До виправлення:**

```javascript
document.querySelector("#description").innerHTML = current.description;
paragraph.innerHTML = comment.text;
```

**Після виправлення:**

```javascript
document.querySelector("#description").textContent = current.description;
paragraph.textContent = comment.text;
```

Використання `textContent` забезпечує відображення недовіреного рядка як звичайного тексту.

Виправлення не потребувало змін до значення в базі даних, видалення HTML-подібних символів або створення власного HTML sanitizer.

**Commit виправлення XSS:** `f2bcf9f`.

## 5. Відповіді на контрольні питання

### 1. Чому значення з бази даних може залишатися недовіреним?

Тому що база даних зберігає інформацію, але не гарантує її безпечності для HTML-контексту. Якщо опис створений користувачем, він може містити HTML-подібний рядок навіть після серверної валідації.

### 2. Що таке source, transformation і sink?

Source — джерело недовірених даних, наприклад поле введення Description.

Transformation — обробка або передавання значення, наприклад JSON-серіалізація та `response.json()`.

Sink — місце використання значення, наприклад `innerHTML` або `textContent` у DOM.

### 3. Чим Stored XSS відрізняється від Reflected та DOM-based XSS?

Stored XSS виникає, коли небезпечне значення зберігається та пізніше відображається користувачеві.

Reflected XSS — коли значення із запиту одразу повертається у відповіді.

DOM-based XSS пов'язаний із небезпечною обробкою значення на стороні браузера.

У нашому випадку збережений опис проходив через клієнтський DOM sink, тому відтворена вразливість має ознаки Stored XSS і небезпечного DOM rendering.

### 4. Чому блокування тегу `<script>` не усуває XSS?

Тому що JavaScript може запускатися через інші HTML-механізми, зокрема обробники подій.

У нашій лабораторній маркер використовував подію `onerror`, тому просте видалення тегів `<script>` не усунуло б проблему.

### 5. Коли використовують textContent, а коли sanitizer?

`textContent` використовують, якщо потрібно відобразити звичайний текст без HTML-форматування.

Sanitizer потрібний лише тоді, коли застосунок свідомо підтримує дозволену підмножину HTML.

У SecureLab поле Description має містити звичайний текст, тому використання `textContent` є правильним рішенням.

### 6. Чому sanitizer не слід писати регулярними виразами?

HTML має складні правила синтаксичного аналізу, кодування та обробки атрибутів.

Регулярні вирази не забезпечують надійного аналізу всіх можливих HTML-контекстів, тому власний sanitizer може пропускати небезпечні конструкції.

### 7. З яких компонентів складається origin?

Origin складається з трьох компонентів: схема, хост і порт.

Наприклад, `http://localhost:4173` та `http://localhost:4174` є різними origins через різні порти.

### 8. Що браузер надсилає під час CORS preflight?

Браузер автоматично надсилає запит `OPTIONS`, який указує майбутній HTTP-метод та певні заголовки запланованого запиту.

Сервер відповідає CORS-заголовками. Браузер використовує їх, щоб вирішити, чи можна надсилати фактичний запит.

Практичний preflight-дослід не виконувався, оскільки належить до вищого рівня.

### 9. Хто оголошує CORS-політику, а хто її застосовує?

Сервер оголошує політику через HTTP-заголовки, зокрема `Access-Control-Allow-Origin`.

Браузер застосовує правила CORS і вирішує, чи дозволити JavaScript прочитати відповідь.

### 10. Чому curl може прочитати відповідь, коли браузер показує CORS error?

Тому що CORS є частиною політики безпеки браузера.

`curl` не застосовує browser same-origin policy, тому може отримувати HTTP-відповіді без перевірки дозволених origins.

Водночас серверна автентифікація та авторизація залишаються обов'язковими.

### 11. Чому CORS не є авторизацією і не замінює CSRF-захист?

CORS контролює доступ браузерного JavaScript до cross-origin відповідей.

Авторизація визначає, чи має користувач право виконувати конкретну операцію над ресурсом.

CSRF-захист протидіє небажаним змінам стану через запити, які браузер може надсилати з обліковими даними користувача.

Тому ці механізми виконують різні завдання.

### 12. Чому wildcard origin не можна поєднувати з credentials?

Для credentialed CORS-запитів браузер потребує конкретного дозволеного origin і заголовка `Access-Control-Allow-Credentials: true`.

Wildcard `*` не може бути використаний для такого дозволу.

### 13. Чому CSP не замінює безпечне DOM rendering?

CSP може обмежувати виконання певних скриптів і завантаження ресурсів, але не усуває саму причину небезпечної HTML-інтерпретації.

Навіть якщо CSP блокує виконання обробника події, `innerHTML` може продовжувати створювати небажані HTML-елементи.

Тому першочерговим виправленням у нашій роботі є `textContent`.

### 14. Який ризик зменшують nosniff, Referrer-Policy і frame-ancestors?

`X-Content-Type-Options: nosniff` обмежує небажане визначення MIME-типу браузером.

`Referrer-Policy: no-referrer` запобігає передаванню інформації Referer під час переходів і запитів.

Директива CSP `frame-ancestors` визначає, які сторінки можуть вбудовувати застосунок у фрейм, і допомагає зменшувати ризик clickjacking.

Практичне налаштування CSP та окрема перевірка цих механізмів не входили до обраного рівня.

## 7. Межі виконання

Лабораторну роботу виконано на рівні «Задовільно».

Фактично перевірено:

- Stored XSS для `Incident.Description`.
- Безпечне відображення того самого маркера після виправлення.
- Результати під Alice та Morgan.
- Негативний контроль доступу Bob до чужого інциденту до виправлення.
- Звичайний текст, Unicode, HTML-подібні символи.
- Опис довжиною 3900 символів.
- CORS для origins `4173` і `4174`.
- Прямі HTTP-запити через `curl.exe`.
- Регресійні автоматичні тести — 11 із 11.

За межами обраного рівня залишилися окреме дослідження XSS у `IncidentComment.Text`, preflight, credentialed CORS, CSP enforcement та автоматизований браузерний DOM-тест.

Обидва небезпечні `innerHTML` у наданому `browser-lab.js` виправлено.

Залишковий ризик полягає в можливості наявності інших недосліджених DOM sinks та необхідності окремого CSRF-захисту змінювальних операцій із cookie authentication.

## 8. Висновки

Під час лабораторної роботи №5 досліджено безпеку браузерного клієнта SecureLab та механізми контролю доступу між різними origins.

Побудовано карту проходження даних `Incident.Description`, визначено небезпечний sink `innerHTML` та експериментально підтверджено Stored XSS у локальному навчальному середовищі.

Вразливість усунуто шляхом використання безпечного DOM API `textContent`. Повторне тестування підтвердило, що маркер більше не виконується, а значення відображається як звичайний текст.

Додатково налаштовано CORS-політику, що дозволяє читати відповіді API лише навчальному origin `http://localhost:4173`.

Перевірка `http://localhost:4174` показала, що браузер не надає JavaScript доступ до відповіді без відповідного CORS-дозволу.

Порівняння з `curl.exe` підтвердило відмінність між браузерною same-origin policy та серверними механізмами авторизації.

Після внесених змін проєкт успішно зібрано, усі 11 автоматичних тестів пройдено.

**Практичну частину лабораторної роботи №5 для рівня «Задовільно» виконано успішно.**
