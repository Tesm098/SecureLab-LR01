## 2. Контракт API та CP-01

У файлі `src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs` розроблено `POST /api/incidents` з окремими типами `CreateIncidentRequest` та `CreatedIncidentResponse`.

**Поля вхідного DTO:** `title`, `description`, `severity`, `occurredAtUtc`. Сервер перевіряє:

1. `title` — обов'язкове після `Trim()`, довжина надісланого рядка не більше **160** символів.
2. `description` — обов'язкове після `Trim()`, довжина надісланого рядка не більше **4000** символів.
3. `severity` — лише `Low`, `Medium`, `High`, `Critical`; використано `Enum.TryParse` та `Enum.IsDefined`.
4. `occurredAtUtc` — обов'язкове; дата не може перевищувати `now + 5 хвилин`, де `now` зафіксовано один раз для запиту.
5. Рядкові поля нормалізуються через `Trim()`, момент інциденту — через `ToUniversalTime()`.

За помилки повертається **400 Bad Request**, `application/problem+json`, із конкретними ключами в `errors`. Ідентифікатор інциденту, власник (`DbSeeder.AliceId`), статус `New` та часові поля створення/оновлення призначаються сервером. `CreatedIncidentResponse` містить лише дозволені поля та не повертає внутрішню сутність цілком.

**Фактичні перевірки CP-01:**

- Коректний POST зі сторонніми `id`, `status=Closed`, `ownerUserId` повернув **201 Created**, але сервер видав власний `id`, статус **New**, severity **Medium**; GET за новим ID повернув **200 OK** і власника **Аліса Коваль**.
- `severity="7"` → **400**, ключ `severity`.
- Відсутня дата → **400**, ключ `occurredAtUtc`.
- Дата `2099-01-01T00:00:00Z` → **400**, ключ `occurredAtUtc`.
- Назва з **161** символу → **400**, ключ `title`.
- Опис із **4001** символу → **400**, ключ `description`.
- Назва й опис лише з пробілів → **400**, ключі `title` і `description`.
- Дата `2026-08-01T13:00:00+03:00` збережена й повернена як `2026-08-01T10:00:00+00:00`; POST → **201**.

Перевірки виконувалися на локальній навчальній базі. Скриншоти CMD і браузера отримано під час власного запуску, їх потрібно додати до комплекту доказів.

## 3. Security-сценарій та CP-02 / CP-03

### Контекст і гіпотеза

Endpoint `GET /api/incidents/search` отримує недовірені параметри `q` і `sortBy`. У стартовій реалізації вони впливали на побудову SQL-тексту, створюючи ризик SQL injection.

### CP-02. Стан до виправлення

У vulnerable commit **`ea2960e`** обробник пошуку в `Lab02Endpoints.cs` формував SQL шляхом конкатенації рядків та виконував його через `db.Incidents.FromSqlRaw(sql)`. Для `sortBy` невідоме значення також могло потрапити до SQL-структури.

На локальному read-only сценарії з `tests/http/lab-02-checks.http` зафіксовано:

- Звичайний пошук за відсутнім значенням `zz-no-match` → **200 OK**, `[]`.
- Той самий запит із навчальним контрольним SQLi-вводом (сценарій **C / S-01**) → **200 OK**, **7 інцидентів** замість порожнього списку. На момент перевірки в БД було п'ять seed-інцидентів і два власні тестові записи.
- Легітимний пошук `O'Brien` до виправлення → **500 Internal Server Error**.
- Журнал EF Core для S-01 показав `Parameters=[]` і потрапляння недовіреної частини умови до SQL-команди.

**Першопричина:** значення параметра HTTP-запиту ставало частиною синтаксису SQL до передавання до PostgreSQL. Цю вразливість не можна коректно усунути простим блокуванням одного апострофа чи конкретної послідовності символів.

### CP-03. Виправлення та повторна перевірка

У fixed commit **`990b20d`** пошук переписано на LINQ та `EF.Functions.ILike` із параметризованим шаблоном. Символи `%`, `_` і `\` екрануються, тому пошук виконується за буквальним підрядком. Для `sortBy` використано allowlist `createdAtUtc`, `severity`, `status`; невідоме значення повертає **400** із ключем `sortBy`.

Контракт сортування: `CreatedAtUtc` за спаданням; severity — `Critical → High → Medium → Low`; status — `New → Triaged → InProgress → Resolved → Closed`; стабільний другий ключ `Id`; `Take(50)` після сортування.

**Фактична регресія:**

- Сценарій **S-02** з тим самим контрольним вводом → **200 OK**, `[]`.
- Пошук `USB` → **200 OK**, один інцидент «Перевірка USB навчальної мережі» (ID закінчується на `0005`).
- Пошук `O'Brien` → **200 OK**, один інцидент «O'Brien classroom report» (ID закінчується на `0004`).
- Пошук буквального `%` через `q=%25` → **200 OK**, `[]`.
- Невідомий `sortBy=price` → **400 Bad Request**, `application/problem+json`, ключ `sortBy`.
- Сортування `severity`, `status`, `createdAtUtc` → **200 OK** із відповідним порядком. На час перевірок було 7 записів; після підсумкового reset навчальна база повернулася до seed.
- У журналі EF Core після fix зафіксовано `Parameters=[@pattern='?', @pattern0='?', @p='?']` та `ILIKE @pattern ... ESCAPE`, що підтверджує відокремлення значень від SQL-структури.

**Git-доказ:** `git diff ea2960e 990b20d -- src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs` показує заміну `FromSqlRaw` на LINQ/`ILike` та додавання allowlist. Порівняння та обидва commits доступні в GitHub: [diff vulnerable → fixed](https://github.com/Tesm098/SecureLab-LR01/compare/ea2960e...990b20d).

## 5. Обмеження і висновок

У роботі реалізовано серверну валідацію створення інциденту та усунуто небезпечне формування SQL у пошуку. Для демонстрації використано лише локальний стенд зі штучними записами; контрольний SQLi-сценарій був **read-only**, без дій на зміну чи видалення даних. Коректність перевірено фактичними HTTP-відповідями, порівнянням Git commits, журналом EF Core та п'ятьма автоматизованими baseline-тестами.

Перевірено вимоги достатнього рівня: T-01, T-02, S-01, S-02, T-04, T-05, контрольні точки CP-01…CP-03. Додаткові вимоги доброго/відмінного рівня (T-03, T-09, A-01 тощо) не заявляються як виконані. Проведені тести не доводять відсутності всіх інших вразливостей системи.
