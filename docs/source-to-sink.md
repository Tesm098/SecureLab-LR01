## 1. Мета дослідження

Метою є встановлення повного шляху проходження значення `Incident.Description` від введення користувачем до відображення у браузері.

Необхідно визначити джерело недовірених даних, серверні та клієнтські перетворення, місце зберігання й кінцевий DOM sink.

Окремо досліджується, чому використання `innerHTML` створює небезпеку XSS та як заміна на `textContent` усуває неправильну інтерпретацію даних.

## 4. Небезпечний DOM sink до виправлення

У початковому коді `browser-lab.js` використовувалася операція:

`document.querySelector("#description").innerHTML = current.description;`

Метод `innerHTML` передає рядок HTML-парсеру браузера.

Якщо рядок містить HTML-подібну структуру, браузер може створювати нові елементи та обробляти їхні події.

Під час досліду використано лише дозволений локальний маркер, який змінює атрибут `data-lab05-marker` прихованого елемента `#lab05-marker-target`.

Перед виконанням контрольна команда повертала:

`null`

Після відображення інциденту Alice:

`'executed'`

У вкладці Elements усередині `#description` було створено справжній HTML-елемент `<img>`.

На сторінці з'являвся значок зламаного зображення.

Отже, підтверджено, що недовірене значення було інтерпретоване як HTML з виконанням обробника події.

## 5. Перевірка Stored XSS в іншому сеансі

Для підтвердження збереженого характеру вразливості створений інцидент було відкрито в окремому приватному вікні браузера.

**Користувач:** Morgan

**Роль:** `Analyst`

Morgan мав предметний дозвіл переглядати інцидент Alice.

Фактичні результати до виправлення:

- HTTP-статус: `200 OK`.
- До відкриття інциденту контрольний атрибут мав значення `null`.
- Після завантаження опису контрольна команда повернула `'executed'`.
- Браузер створив HTML-елемент зі збереженого опису.

Таким чином, значення, введене Alice, було збережено та пізніше виконано в іншому авторизованому сеансі.

**Класифікація:** Stored XSS із небезпечним клієнтським HTML sink.

Термін Stored XSS описує походження та збереження даних, а DOM sink — місце небезпечної інтерпретації.

## 6. Виправлення небезпечного відображення

У файлі:

`src/SecureLab.Api/Client/browser-lab.js`

виконано такі заміни:

**До виправлення:**

```javascript
document.querySelector("#description").innerHTML = current.description;
```

**Після виправлення:**

```javascript
document.querySelector("#description").textContent = current.description;
```

Також виправлено відображення коментарів:

**До виправлення:**

```javascript
paragraph.innerHTML = comment.text;
```

**Після виправлення:**

```javascript
paragraph.textContent = comment.text;
```

Структура елементів створюється кодом JavaScript, а недовірені значення відображаються як текст.

Серверне значення `description` не змінювалося. Для усунення вразливості не застосовувалися чорні списки тегів, регулярні вирази чи видалення кутових дужок.

Це підтверджує, що усунено першопричину XSS, а не лише змінено вхідне значення.

## 8. Інвентаризація DOM sinks

Межа інвентаризації — власний навчальний клієнт `browser-lab.js` і перевірений штатний клієнт `app.js`.

| Файл / функція | Дані | Категорія | Контекст | Рішення |
|---|---|---|---|---|
| `browser-lab.js`, `load()`, `#title` | `current.title` | Збережене значення користувача | Text node | `textContent`, безпечно |
| `browser-lab.js`, `load()`, `#description` | `current.description` | Збережене значення користувача | До виправлення HTML parser; після виправлення text node | `innerHTML` замінено на `textContent` |
| `browser-lab.js`, `load()`, `#comments` | `comment.text` | Збережене значення користувача | До виправлення HTML parser; після виправлення text node | `innerHTML` замінено на `textContent` |
| `browser-lab.js`, `load()`, `#status` | HTTP-статус | Результат серверного запиту | Text node | `textContent`, безпечно |
| `browser-lab.js`, `submit`, `#status` | HTTP-статус створення | Результат серверного запиту | Text node | `textContent`, безпечно |
| `browser-lab.js`, форма `#edit` | `current.description` | Збережене значення користувача | Властивість `value` поля форми | Значення присвоюється як текст, без HTML parsing |
| `app.js`, відображення назви | `incident.title` | Збережене значення користувача | Text node | Безпечне текстове відображення через `textContent` |

Текст коментарів також виправлено, оскільки методичні рекомендації вимагають, щоб у кінцевому стані жодне значення з API не потрапляло в небезпечний `innerHTML`.

Окремий експеримент із XSS-маркером у `IncidentComment.Text` не виконувався, оскільки належить до рівнів «Добре» та «Відмінно».

## 9. Позитивна регресія

Окремо перевірено звичайний текст:

`O'Brien написав "Київ — Ω"; 5 < 7 і 9 > 3; <b>жирний</b> текст.`

До виправлення слово «жирний» відображалося напівжирним, оскільки браузер створював елемент `<b>`.

Після виправлення весь рядок, зокрема `<b>жирний</b>`, відображався буквально.

У Elements підтверджено відсутність дочірнього HTML-елемента `<b>`.

Також створено тестовий інцидент:

`LR05 Long text regression`

Його опис містив 3900 символів «А».

Після збереження та повторного читання перевірено:

`document.querySelector("#description").textContent.length`

Фактичний результат:

`3900`

Отже, виправлення не пошкодило Unicode, лапки, HTML-подібний текст і довгі значення в межах дозволеної довжини.

## 10. Підсумковий finding

**Назва:** Stored XSS через небезпечне відображення `Incident.Description`.

**Актив:** Дані інцидентів та браузерні сеанси авторизованих користувачів.

**Передумови:** Можливість створити навчальний інцидент із контрольованим текстом опису та право іншого користувача його переглянути.

**Першопричина:** Передавання недовіреного значення `current.description` до `innerHTML`.

**Підтверджений вплив:** Виконання нешкідливого локального маркера в сеансах Alice та Morgan.

**Виправлення:** Заміна `innerHTML` на `textContent` для опису та коментарів.

**Retest:** Те саме значення відображається буквально, HTML-елемент не створюється, контрольний маркер повертає `null`.

**Залишковий ризик:** Інші недосліджені DOM sinks, сторонні скрипти та контексти виведення, зокрема URL і атрибути, можуть потребувати окремої перевірки.

## 11. Висновок

У лабораторній роботі №5 побудовано карту проходження недовіреного значення `Incident.Description` від введення користувачем до браузерного DOM.

Доведено, що збереження даних у PostgreSQL і передавання через JSON не роблять їх довіреним HTML.

Виявлено небезпечний sink `innerHTML`, через який збережений опис інциденту інтерпретувався браузером як HTML та виконував навчальний JavaScript-обробник.

Після заміни `innerHTML` на `textContent` повторний експеримент підтвердив відсутність виконання маркера за незмінного вмісту опису.

Додатково підтверджено правильне відображення HTML-подібного тексту, Unicode та опису довжиною 3900 символів.

**Основну карту source-to-sink і дослідження XSS для рівня «Задовільно» завершено успішно.**
