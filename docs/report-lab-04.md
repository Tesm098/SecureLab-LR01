## 2. Матриця доступу і серверне рішення

### 2.1. Вибрана захищена операція

Головною операцією ЛР №4 обрано:

`GET /api/incidents/{id}`

Вона повертає детальну інформацію про конкретний інцидент.

Документ із матрицею контролю доступу:

`docs/access-matrix.md`

### 2.2. Правила авторизації

| Суб'єкт | Дія | Очікуване рішення |
|---|---|---|
| Анонімний користувач | Перегляд деталей інциденту | `401 Unauthorized` |
| Alice, Reporter | Перегляд власного інциденту | `200 OK` |
| Alice, Reporter | Перегляд інциденту Bob | `404 Not Found` |
| Bob, Reporter | Перегляд власного інциденту | `200 OK` |
| Morgan, Analyst | Перегляд інциденту Alice | `200 OK` |
| Administrator | Перегляд чужого інциденту без окремого дозволу | `404 Not Found` |

Власник ресурсу визначається за полем `OwnerUserId`.

Наявність однакової ролі Reporter у Alice та Bob не означає, що вони мають доступ до інцидентів одне одного.

Роль Analyst має право читання інцидентів для аналітичних завдань, але не отримує автоматичного права довільно їх змінювати або видаляти.

### 2.3. Політика відмови

Для чужого ресурсу обрано HTTP `404 Not Found`.

Це рішення дозволяє не повідомляти користувачеві без відповідних прав, чи існує конкретний чужий інцидент.

Для чужого та неіснуючого ресурсу реалізовано спільний спосіб формування відповіді з назвою «Інцидент не знайдено».

Ідентифікатор поточного користувача визначає сервер на підставі перевіреного `HttpContext.User`. Ідентифікатор у URL використовується лише для пошуку ресурсу і не є доказом права доступу.

### 2.4. Межа реалізації

На достатньому рівні реалізовано авторизацію головної операції перегляду деталей інциденту.

Контроль доступу до списку, пошуку, агрегованих даних, зміни, видалення, triage та дочірніх ресурсів не включено до обраного обсягу ЛР №4.

Успадкований із ЛР №3 контракт створення інциденту зберігає серверне призначення власника.

## 3. Вразливий стан і PoC

### 3.1. Контекст дослідження

До виправлення endpoint перегляду деталей інциденту знаходив ресурс за його ідентифікатором, не застосовуючи перевірку права доступу конкретного користувача.

Для дослідження використано два навчальні інциденти:

| Ресурс | Ідентифікатор | Власник |
|---|---|---|
| incident-1 | `20000000-0000-0000-0000-000000000001` | Alice |
| incident-2 | `20000000-0000-0000-0000-000000000002` | Bob |

### 3.2. Гіпотеза

Припускалося, що автентифікована Alice зможе отримати деталі інциденту Bob, змінивши лише ідентифікатор ресурсу в HTTP-запиті.

Така поведінка є прикладом горизонтального порушення контролю доступу — IDOR/BOLA.

### 3.3. Дозволений запит Alice до власного ресурсу

Команда:

`py -3 ..\lr04-resources\commands\login-and-read.py --user alice --incident alice`

Фактичний результат:

- `login_status=204`
- `read_status=200`
- ID ресурсу: `20000000-0000-0000-0000-000000000001`
- Власник: Аліса Коваль.
- Назва: «Підозрілий лист із вкладенням».

Результат відповідає очікуваній політиці доступу.

### 3.4. Несанкціонований запит Alice до ресурсу Bob

Команда:

`py -3 ..\lr04-resources\commands\login-and-read.py --user alice --incident bob`

Очікувано за матрицею:

`404 Not Found`

Фактично до виправлення:

- `login_status=204`
- `read_status=200`
- ID ресурсу: `20000000-0000-0000-0000-000000000002`
- Назва інциденту: «Невідома спроба входу».
- Власник: Боб Мельник.

Таким чином, Alice змогла прочитати чужий інцидент, хоча мала роль Reporter і не була його власником.

**Вразливість IDOR/BOLA підтверджено фактичним HTTP-запитом.**

### 3.5. Перевірка Morgan

Команда:

`py -3 ..\lr04-resources\commands\login-and-read.py --user morgan --incident alice`

Фактичний результат до виправлення:

- `login_status=204`
- `read_status=200`

Morgan зміг прочитати інцидент Alice.

На початковому етапі цей результат підтверджував доступність ресурсу, але ще не доводив, що сервер правильно застосовував роль Analyst.

Тому після виправлення сценарій перевірено повторно.

### 3.6. Першопричина

Першопричина вразливості знаходилася в реалізації отримання деталей інциденту.

Файл:

`src/SecureLab.Api/Application/Incidents/IncidentQueries.cs`

Початкова умова вибірки:

`incident.Id == id`

Вона перевіряла лише ідентифікатор запитуваного ресурсу.

Перевірки `OwnerUserId` та ролі поточного користувача не було.

Відповідно, endpoint міг повертати дані чужого інциденту без належного ресурсного рішення.

Сам по собі ідентифікатор у URL не є вразливістю. Вразливість полягає у відсутності серверної перевірки права доступу до знайденого ресурсу.

### 3.7. Git-фіксація вразливого стану

Початковий вразливий стан збережено окремим commit.

**Vulnerable commit:**

`89e7e2a1f9979e8bdef15c993bed2f718373cc38`

Повідомлення commit:

`Document vulnerable IDOR state and access matrix`

У цьому commit збережено матрицю, початковий звіт та відтворюваний HTTP-сценарій.

Вихідний код у цей момент ще містив підтверджену вразливість.

Commit призначений для локального навчального дослідження і не повинен публікуватися у відкритому репозиторії.

## 4. Виправлення та retest

### 4.1. Реалізація захисту

Після підтвердження вразливості реалізовано серверну авторизацію для операції:

`GET /api/incidents/{id}`

Зміни внесено до двох файлів:

1. `src/SecureLab.Api/Presentation/Endpoints/IncidentEndpoints.cs`
2. `src/SecureLab.Api/Application/Incidents/IncidentQueries.cs`

### 4.2. Захист endpoint

У `IncidentEndpoints.cs` виконано такі зміни:

- Додано `RequireAuthorization()` для маршруту деталей інциденту.
- Ідентифікатор поточного користувача береться з `ClaimTypes.NameIdentifier` у перевіреному principal.
- Роль Analyst перевіряється сервером через `IsInRole`.
- Ідентифікатор користувача передається до методу отримання деталей.
- Для чужого або неіснуючого інциденту повертається `404 Not Found`.

Таким чином, сервер більше не використовує довільні клієнтські дані як підтвердження особи.

### 4.3. Обмеження запиту до бази даних

У `IncidentQueries.cs` змінено метод `GetDetailsAsync`.

До перевірки ID ресурсу додано умову доступу:

`isAnalyst || incident.OwnerUserId == currentUserId`

Тепер запит повертає інцидент лише тоді, коли виконується хоча б одна з умов:

- Користувач є власником інциденту.
- Користувач має перевірену сервером роль Analyst.

Для звичайного Reporter чужий інцидент не потрапляє до результату запиту.

Це рішення працює на сервері, до формування HTTP-відповіді.

### 4.4. Повторне тестування

Після внесення змін виконано ті самі HTTP-сценарії.

| Сценарій | До виправлення | Після виправлення | Результат |
|---|---|---|---|
| Alice → власний інцидент | `200 OK` | `200 OK` | Дозволений доступ збережено |
| Alice → інцидент Bob | `200 OK` | `404 Not Found` | IDOR/BOLA усунено для головної операції |
| Morgan → інцидент Alice | `200 OK` | `200 OK` | Аналітичний перегляд збережено |

Під час повторного запиту Alice до інциденту Bob сервер повернув:

- `login_status=204`
- `read_status=404`
- `title`: «Інцидент не знайдено»
- `status`: `404`

Дані Bob, назва його інциденту та ім'я власника не потрапили до відповіді.

### 4.5. Автоматизовані тести

До файлу:

`tests/SecureLab.Api.Tests/IncidentEndpointTests.cs`

додано два автоматизовані HTTP-тести.

**A-02 — `A02_Owner_CanReadOwnIncident`**

Тест виконує справжній вхід Alice, запитує її власний інцидент і перевіряє HTTP `200 OK` та правильність ID ресурсу.

**A-03 — `A03_NonOwner_CannotReadForeignIncident`**

Тест виконує справжній вхід Alice, запитує інцидент Bob і перевіряє:

- HTTP `404 Not Found`.
- Тип відповіді `application/problem+json`.
- Відсутність ID Bob у тілі.
- Відсутність імені Боба Мельника у відповіді.

Обидва автоматизовані тести пройдено успішно:

`Test summary: total: 2, failed: 0, succeeded: 2`

**A-03R — Morgan → Alice**

Перевірено повторюваним HTTP-запитом через `login-and-read.py`.

Результат: `204` для входу та `200` для читання інциденту.

### 4.6. Регресійне тестування

Два попередні тести, успадковані з ЛР №1, спочатку завершувалися помилкою, оскільки очікували доступ без автентифікації.

Їх оновлено для використання автентифікованого клієнта.

Захист endpoint для проходження старих тестів не послаблювався.

### 4.7. Узгодженість HTTP 404

## 6. Основний finding і залишковий ризик

### 6.1. Основний finding

**Назва:** Несанкціонований перегляд чужого інциденту через IDOR/BOLA.

**Контекст:** SecureLab, `GET /api/incidents/{id}`.

**Передумови:** Автентифікований користувач Alice з роллю Reporter і навчальний інцидент Bob.

**Гіпотеза:** Зміна ідентифікатора ресурсу дозволяє Alice прочитати чужі дані.

**Стан до виправлення:** HTTP `200 OK`, повертаються дані Bob.

**Першопричина:** Запит до бази перевіряв лише ID інциденту, але не перевіряв власника або роль поточного користувача.

**Виправлення:** Впроваджено перевірку authenticated principal, роль Analyst та обмеження вибірки за `OwnerUserId`.

**Стан після виправлення:** HTTP `404 Not Found`, чужі дані не повертаються.

**Позитивна регресія:** Alice читає власний інцидент, Morgan читає інцидент для аналізу.

**Доказ:** HTTP-перевірки, тести A-02/A-03, повторюваний сценарій A-03R та браузерні перевірки.

### 6.2. Залишковий ризик

На достатньому рівні захищено головну операцію перегляду деталей.

Інші маршрути, зокрема отримання списку, пошук та підсумкова статистика, не охоплювалися повною ресурсною авторизацією в межах цього завдання.

Через це потенційні ризики розкриття чужих даних іншими шляхами залишаються предметом подальшого дослідження.

Також для cookie-автентифікації змінювальних операцій актуальним є захист від CSRF, який належить до наступних етапів лабораторного курсу.

## 12. Висновок

У ході лабораторної роботи №4 досліджено механізми контролю доступу до інцидентів у застосунку SecureLab.

Побудовано матрицю доступу для головної захищеної операції `GET /api/incidents/{id}` та встановлено правила для ролей Reporter і Analyst.

У початковому стані виявлено вразливість IDOR/BOLA: користувач Alice міг прочитати інцидент Bob, змінивши лише ідентифікатор ресурсу.

Для усунення вразливості реалізовано серверну перевірку authenticated principal, ролі та володіння ресурсом.

Після виправлення запит Alice до інциденту Bob повертає `404 Not Found`, тоді як перегляд власного інциденту Alice та аналітичний перегляд Morgan залишаються дозволеними.

Результати підтверджено автоматизованими HTTP-тестами A-02 і A-03, повторюваним запитом A-03R та браузерними перевірками.

Після внесення змін повний набір із 11 автоматичних тестів завершився успішно.
